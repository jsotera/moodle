    4.1 Modularización: combate de personajes

    En esta actividad aprenderás a modularizar código. Partiremos de una clase Codigo1 que contiene todo en un único método y varios atributos, y la tarea será reorganizarla en clases y métodos coherentes con nombres claros y responsables.

    Código base a modularizar

    Esta es la clase que vamos a usar como punto de partida:

    public class Codigo1 {

    public String nombre1;
    public int vida1;
    public int ataque1;
    public int defensa1;

    public String nombre2;
    public int vida2;
    public int ataque2;
    public int defensa2;

    public void blablabla() {

        nombre1 = "R2D2";
        vida1 = 100;
        ataque1 = (int) (Math.random() * 10) + 5;
        defensa1 = (int) (Math.random() * 10) + 5;

        nombre2 = "C3P0";
        vida2 = 100;
        ataque2 = (int) (Math.random() * 10) + 5;
        defensa2 = (int) (Math.random() * 10) + 5;

        System.out.println("Comienza el combate");

        while(vida1>0 && vida2>0) {

            System.out.println("Recalculando stats");

            ataque1 = (int) (Math.random() * 10) + 5;
            defensa1 = (int) (Math.random() * 10) + 5;

            ataque2 = (int) (Math.random() * 10) + 5;
            defensa2 = (int) (Math.random() * 10) + 5;

            String s = "Los stats de " + nombre1 + " son:";
            s += "\n\tvida: " + vida1;
            s += "\n\tataque: " + ataque1;
            s += "\n\tdefensa: " + defensa1;
            System.out.println(s);

            s = "Los stats de " + nombre2 + " son:";
            s += "\n\tvida: " + vida2;
            s += "\n\tataque: " + ataque2;
            s += "\n\tdefensa: " + defensa2;
            System.out.println(s);

            if (ataque1 > defensa2) {
                vida2 = vida2 - (ataque1 - defensa2);
                if (vida2 <= 0) {
                    vida2 = 0;
                    System.out.println("GRRR..." + nombre2 + " PERDER COMBATE...BSSSS");
                }
            }
            if (ataque2 > defensa1) {
                vida1 = vida1 - (ataque2 - defensa1);
                if (vida1 <= 0) {
                    vida1 = 0;
                    System.out.println("GRRR..." + nombre1 + " PERDER COMBATE...BSSSS");
                }
            }
        }

        if(vida1 > vida2){
            System.out.println(nombre1+" se alza con la victoria");
        } else if (vida1 < vida2) {
            System.out.println(nombre2+" se alza con la victoria");
        } else {
            System.out.println("Ha sido un combate con empate");
        }
    }

}

    Como puedes ver, todo está en una única clase y un único método. Esto dificulta la lectura, el mantenimiento y la reutilización del código.

    Objetivo de la modularización

    La tarea consiste en:

    • Crear una clase XXX (elegir un nombre coherente) que represente a cada personaje del combate.
    • Crear métodos dentro de la clase para acciones concretas, por ejemplo: decirEdad(), cantar(int tiempo), etc.
    • Recordad, dividir el código en métodos pequeños y significativos para que cada parte tenga una única responsabilidad.
    • Elegir nombres claros y descriptivos para clases y métodos.

    4.2 Modularización: carrera de coches

    Vamos a seguir modularizando código. Volvéis a tener una clase, ahora se llama Codigo2, que contiene todo en un único método y varios atributos. Recordad, la tarea será reorganizarla en clases y métodos coherentes con nombres claros y responsables.

    Código base a modularizar

    Esta es la clase que vamos a usar como punto de partida:

    public class Codigo2 {

    public String coche1;
    public int velocidad1;
    public int distancia1;

    public String coche2;
    public int velocidad2;
    public int distancia2;

    public void blablabla() {
        coche1 = "Rayo";
        distancia1 = 0;

        coche2 = "Trueno";
        distancia2 = 0;

        for (int i = 0; i < 10; i++) {
            velocidad1 = (int)(Math.random() * 20) + 5;
            velocidad2 = (int)(Math.random() * 20) + 5;

            distancia1 += velocidad1;
            distancia2 += velocidad2;

            System.out.println(coche1 + " avanza " + velocidad1 + " metros. Total: " + distancia1);
            System.out.println(coche2 + " avanza " + velocidad2 + " metros. Total: " + distancia2);
        }

        if (distancia1 > distancia2) {
            System.out.println(coche1 + " gana la carrera!");
        } else if (distancia2 > distancia1) {
            System.out.println(coche2 + " gana la carrera!");
        } else {
            System.out.println("Empate en la carrera!");
        }
    }
}

    4.3 Modularización: combate por turnos

    Si, vamos a darle una vuelta a esto de modularizar código. Ahora tenéis una clase Codigo3. ¡Esta vez tiene más miga, leer los comentarios! Recordad, la tarea será reorganizarla en clases y métodos coherentes con nombres claros y responsables.

    Código base a modularizar

    Esta es la clase que vamos a usar como punto de partida:

    public class Codigo3 {

    public int h1; // vida jugador1
    public int h2; // vida jugador2
    public int m1; // mana jugador1
    public int m2; // mana jugador2
    public int e1; // vida enemigo1
    public int e2; // vida enemigo2
    public int em1; // mana enemigo1
    public int em2; // mana enemigo2

    public void blablabla() {
        h1 = 100; m1 = 50;
        h2 = 100; m2 = 50;
        e1 = 80; em1 = 40;
        e2 = 80; em2 = 40;

        java.util.Random rnd = new java.util.Random();

        int turno = 1; // 1 = jugador1, 2 = jugador2

        for (int i = 0; i < 20; i++) {
            System.out.println("=== Nuevo turno ===");

            if (turno == 1 && h1 > 0) {
                System.out.println("Jugador 1: vida " + h1 + ", mana " + m1);
                int op = (int) (Math.random()*3)+1;
                int dmg = 5, cost = 0;
                if (op == 1) { dmg = 15; cost = 10; }
                if (op == 2) { dmg = 25; cost = 15; }
                if (op == 3) { dmg = 40; cost = 20; }

                if (m1 >= cost) {
                    m1 -= cost;
                    if (e1 > 0) e1 -= dmg;
                    else e2 -= dmg;
                    System.out.println("Jugador1 hace " + dmg + " daño");
                } else {
                    System.out.println("No tienes mana suficiente!");
                }
                turno = 2;
            } else if (turno == 2 && h2 > 0) {
                System.out.println("Jugador 2: vida " + h2 + ", mana " + m2);
                int op = (int) (Math.random()*3)+1;
                int dmg = 5, cost = 0;
                if (op == 1) { dmg = 15; cost = 10; }
                if (op == 2) { dmg = 25; cost = 15; }
                if (op == 3) { dmg = 40; cost = 20; }

                if (m2 >= cost) {
                    m2 -= cost;
                    if (e1 > 0) e1 -= dmg;
                    else e2 -= dmg;
                    System.out.println("Jugador2 hace " + dmg + " daño");
                } else {
                    System.out.println("No tienes mana suficiente!");
                }
                turno = 3;
            } else {
                if (e1 > 0) {
                    int op = (int) (Math.random()*3)+1;
                    int dmg = 5, cost = 0;
                    if (op == 1) { dmg = 10; cost = 5; }
                    if (op == 2) { dmg = 20; cost = 10; }
                    if (op == 3) { dmg = 30; cost = 15; }

                    if (em1 >= cost) {
                        em1 -= cost;
                        if (h1 > 0) h1 -= dmg;
                        else h2 -= dmg;
                        System.out.println("Enemigo1 hace " + dmg + " daño");
                    } else {
                        System.out.println("Enemigo1 no tiene mana suficiente");
                    }
                }

                if (e2 > 0) {
                    int op = (int) (Math.random()*3)+1;
                    int dmg = 5, cost = 0;
                    if (op == 1) { dmg = 10; cost = 5; }
                    if (op == 2) { dmg = 20; cost = 10; }
                    if (op == 3) { dmg = 30; cost = 15; }

                    if (em2 >= cost) {
                        em2 -= cost;
                        if (h1 > 0) h1 -= dmg;
                        else h2 -= dmg;
                        System.out.println("Enemigo2 hace " + dmg + " daño");
                    } else {
                        System.out.println("Enemigo2 no tiene mana suficiente");
                    }
                }
                turno = 1;
            }

            System.out.println("Estado -> J1: " + h1 + "/" + m1 + ", J2: " + h2 + "/" + m2 +
                    " | E1: " + e1 + "/" + em1 + ", E2: " + e2 + "/" + em2);
        }

        if (h1 > 0 || h2 > 0) System.out.println("¡Los jugadores han ganado!");
        else System.out.println("¡Los enemigos han ganado!");
    }
}

    4.5 Diseña una clase con TODO

    En esta actividad vamos a trabajar el diseño de clases y la comprensión del código ajeno. Esta vez tú serás la persona que diseña una clase con TODOs, y otro/a compañero/a será quien tenga que completarla. De esta forma practicarás cómo estructurar código, dar instrucciones claras y trabajar en equipo sobre el mismo diseño.

    Instrucciones de la actividad

    • Crea una clase Java original (por ejemplo: CuentaBancaria, Robot, Juego, Inventario, etc.).
    • Tu clase deberá contener al menos 3 atributos y 5 métodos (no de olvides del constructor).
    • En lugar de implementar el código de los métodos, escribe comentarios con // TODO: explicando claramente qué debe hacer cada método.
    • Las explicaciones deben ser claras y concisas, de modo que otra persona pueda completar el código sin dificultad, pero sin que le des la solución exacta.
    • No se permite el uso de IA: esta actividad busca fomentar el pensamiento lógico y la capacidad de planificación. Si lo hace una máquina por nosotros, no aprendemos.

    Cuando termines tu clase, compártela con un/a compañero/a de clase. Esa persona deberá completar los métodos según tus indicaciones.

    Fases del trabajo colaborativo

    1. Diseño: Crea tu clase con los TODOs siguiendo los requisitos.
    2. Intercambio: Envía tu clase a un/a compañero/a (o el profesor asignará parejas).
    3. Implementación: Completa la clase que te ha tocado rellenando los TODOs.
    4. Revisión: Devuelve la clase a su autor/a original para que revise si cumple con la intención del diseño.

    Requisitos mínimos

    • La clase debe tener un mínimo de 3 atributos.
    • Debe incluir al menos 5 métodos y 1 constructor.
    • Los nombres de los atributos y métodos deben ser coherentes y seguir buenas prácticas (camelCase, nombres descriptivos, etc.).
    • Las instrucciones de los TODO deben ser comprensibles, pero no una guía paso a paso con código exacto.
    • No está permitido usar herramientas de IA para generar los TODOs. Esta actividad es de diseño y pensamiento propio.

    💡 Pista: si te cuesta pensar los TODOs desde cero, crea primero una versión funcional de tu clase, pruébala y, cuando funcione, elimina el código de los métodos sustituyéndolo por comentarios TODO que indiquen lo que hacía cada parte.

    4.6 Clase de utilidades: GeneradorPalabras

    En esta actividad, vamos a dar nuestros primeros pasos en la creación de una clase de utilidades, similar a cómo hemos estado utilizando la clase Math en nuestros proyectos. La idea es que aprendáis a crear métodos y constantes estáticas, para que puedan ser invocadas sin necesidad de instanciar la clase.

    Estructura del Proyecto

    • El proyecto deberá estar contenido dentro del paquete: edu.masanz.da.ut4.
    • Crearéis una clase llamada GeneradorPalabras, que estará alojada en un subpaquete denominado util, es decir: edu.masanz.da.ut4.util.
    • Esta clase GeneradorPalabras incluirá una constante y un método estático, que podréis invocar directamente desde la clase Main.

     Requisitos de la Clase GeneradorPalabras

    • Constante estática: Crear una constante llamada PALABRAS que contenga un String con muchas palabras de la misma longitud, separadas por espacios. Por ejemplo: "gato vaca rana leon osos".
    • Método estático: Incluir un método llamado obtenerPalabra(), que devuelva una palabra aleatoria de la constante PALABRAS. Para seleccionar la palabra, utilizaréis métodos del objeto String como charAt, length y substring. Ten en cuenta que no conocemos ni el número de letras que compone cada palabra ni el número de palabras que hay en la constante.

     Uso de la Clase GeneradorPalabras

    En la clase Main, invocaréis al método obtenerPalabra() de la clase GeneradorPalabras para mostrar una palabra aleatoria en pantalla. La clave aquí es que, al ser un método estático, no necesitaréis instanciar la clase GeneradorPalabras para invocarlo, de la misma forma que utilizáis Math.random() sin crear un objeto de tipo Math.

    4.7 Colores para la consola

    En esta actividad, crearéis otra clase de utilidad llamada ColoresConsola. Esta clase os permitirá cambiar el color del texto que se muestra en la consola. Utilizaremos códigos de escape ANSI para modificar el color de la salida, lo que hará que vuestros programas sean más dinámicos y visualmente atractivos.

    Estructura del Proyecto

    • El proyecto estará contenido en el paquete: edu.masanz.da.ut4.util.
    • Crearéis una clase llamada ColoresConsola, que contendrá constantes y métodos estáticos para cambiar el color del texto en consola.

    Constantes para los Colores

    En la clase ColoresConsola, deberéis definir las siguientes constantes para cambiar el color del texto:

    public static final String RESET = "\u001B[0m";
public static final String ROJO = "\u001B[31m";
public static final String VERDE = "\u001B[32m";
public static final String AMARILLO = "\u001B[33m";
public static final String AZUL = "\u001B[34m";
public static final String MAGENTA = "\u001B[35m";
public static final String CIAN = "\u001B[36m";
public static final String BLANCO = "\u001B[37m";

    Estas constantes representan los colores que podréis utilizar para modificar la salida de texto en la consola. La constante RESET se utiliza para volver al color predeterminado.

    Métodos Estáticos

    La clase ColoresConsola también deberá incluir métodos estáticos que permitan mostrar texto en la consola con los colores definidos. Algunos ejemplos de métodos que podríais implementar:

    • imprimirEnRojo(String texto): Muestra el texto en color rojo.
    • imprimirEnVerde(String texto): Muestra el texto en color verde.
    • imprimirEnAmarillo(String texto): Muestra el texto en color amarillo.
    • imprimirEnAzul(String texto): Muestra el texto en color azul.
    • Cada método debe utilizar la constante de color correspondiente, seguido de RESET para volver al color predeterminado.

    Ejemplo de Uso

    En la clase Main, podréis probar la clase ColoresConsola invocando los métodos de colores sin necesidad de crear una instancia. Por ejemplo:

    ColoresConsola.imprimirEnRojo("Este es un mensaje en rojo");
ColoresConsola.imprimirEnVerde("Este es un mensaje en verde");

    Notaréis cómo cambia el color de la salida en la consola, haciendo el texto más visual y llamativo.

    Desafío Adicional

    • Añadid métodos adicionales para otros colores o incluso combinaciones de colores.
    • Intentad crear un método que permita cambiar el color de cualquier texto pasado como parámetro, sin necesidad de definir un método específico para cada color.

    4.8 Wordle por consola

    ¡Ha llegado el momento de poner a prueba todo lo que habéis aprendido hasta ahora! En esta actividad, desarrollaremos un juego de Wordle en consola, utilizando las clases de utilidad que creasteis anteriormente: GeneradorPalabras y ColoresConsola.

    Estructura del Proyecto

    • El proyecto estará contenido en el paquete: edu.masanz.da.ut4.wordle.
    • Crearéis una nueva clase llamada Wordle, que será la clase principal del juego.
    • La clase GeneradorPalabras será utilizada para obtener la palabra del día.
    • La clase ColoresConsola permitirá cambiar los colores de salida en la consola.
    • Deberás crear cada clase en el paquete que consideres oportuno.

    Requisitos

    La clase Wordle deberá cumplir los siguientes requisitos:

    • Tendrá dos constructores. Uno que reciba la palabra del día a evaluar y otro sin parámetros, en cuyo caso deberá generar la palabra del día a evaluar a través del método estático obtenerPalabra() de la clase GeneradorPalabras.
    • Implementará un método evaluarPalabra(String palabraUsuario) que reciba la palabra introducida por el usuario y muestre un resultado formateado con colores según las siguientes reglas:
      • Si la letra no está en la palabra del día, se mostrará la letra en color rojo.
      • Si la letra está en la palabra del día, pero no en la posición correcta, se mostrará la letra en color amarillo.
      • Si la letra está en la posición correcta, se mostrará la letra en color verde.

    Ejemplo de Salida

    Imaginad que la palabra del día es PERRO. Si el usuario introduce la palabra PARTE, el método evaluarPalabra debería devolver algo similar a:

    PARTE

    En este ejemplo:

    • P es correcta y está en la posición correcta (color verde).
    • A está en la palabra del día, pero en una posición incorrecta (color amarillo).
    • R, T y E no están en la palabra del día (color rojo).

    Pistas y Consejos

    • Recordad utilizar los métodos charAt, length y substring de la clase String para recorrer y comparar las letras de la palabra del día.
    • Utilizad las constantes de color definidas en ColoresConsola para mostrar el resultado con los colores adecuados.
    • Intentad hacer que el juego sea intuitivo y que el usuario pueda probar varias palabras hasta adivinar la palabra del día.
    • ¡Únicamente habrá 6 intentos para adivinar la palabra!

    4.9 Tabla de puntuaciones

    En esta actividad, vamos a seguir practicando con cadenas de texto y colores en consola. Además, utilizaremos el método printf para alinear el texto y mostrar una tabla de puntuaciones de forma elegante.

    Descripción del Proyecto

Es decir, se introducirá un nombre y se generará una puntuación aleatoria asignada a dicho nombre. Cuando el usuario introduzca una palabra vacía el programa dejará de solicitar más nombres y mostrará una tabla con tres columnas: Jugador, Puntuación y Rango. El rango estará coloreado según la puntuación del jugador:

    En este ejemplo:

    • La columna de Jugador está alineada a la izquierda.

    Pistas

    4.10 Juego del ahorcado: toma de requisitos

    En esta actividad, vais a diseñar e implementar vuestra propia versión del clásico juego del Ahorcado. El reto es que debéis pensar por vosotros mismos las clases, métodos y atributos necesarios para llevar a cabo la solución. ¡Vamos allá!

    Toma de Requisitos

    Un cliente ha venido a vosotros con la siguiente propuesta:

    "Quiero desarrollar un juego del Ahorcado donde el usuario pueda adivinar palabras. El juego debe permitir al jugador introducir letras una a una y mostrar el progreso de la palabra oculta, actualizando el estado del juego según los intentos fallidos. Además, me gustaría que el jugador pueda ver un contador de los intentos restantes y que el juego termine cuando acierte toda la palabra o agote sus intentos."

    Requisitos del Juego

    4.14 Ampliación: pesca sostenible

    En esta parte del ejercicio, vamos a ampliar la simulación introduciendo una situación mucho más realista y compleja: varios pescadores que comparten el mismo océano. Además, el Océano no solo contiene peces, sino que también tiene un nuevo atributo: su nivel de contaminación. Este valor influirá directamente en la capacidad del océano para regenerar peces y cada vez que un pescador pesque un pez, modificará este valor.

    De esta forma, veremos claramente cómo un mismo objeto compartido puede verse afectado por las acciones de diferentes instancias de otros objetos.

    • Crea al menos tres pescadores distintos, cada uno con su propio nombre e historial de pesca.
    • Todos ellos deben pescar en el mismo objeto Oceano.
    • El océano tendrá un nivel de contaminación entre 0 y 100. La probabilidad de regenerar peces disminuirá según aumente ese valor.
    • Después de que cada pescador pesque, el océano debe intentar regenerarse, afectado por su nivel de contaminación.
    • El nivel de contaminación será compartido por todos, por lo que las acciones de un pescador afectan al resto.
    • El pescador podrá limpiar el océano con un nuevo método limpiarOceano(Oceano o). Podrá elegir está opción en base a una probabilidad o el criterio que elijáis, pero nunca podrá pescar y limpiar el océano al mismo tiempo. 

    Por ejemplo, si un pescador es muy activo y contamina mucho, los demás notarán que el océano se regenera con más dificultad. Esto permite observar con claridad el concepto de paso por referencia: todos los pescadores están actuando sobre el mismo objeto en memoria, no sobre copias.

    💡 Reflexión: Este tipo de situación refleja perfectamente lo que ocurre en la programación cuando varios objetos modifican una misma referencia. Cambiar el estado del objeto compartido desde uno de ellos afecta al resto, y eso puede provocar consecuencias inesperadas si no se gestiona bien.
    Retos adicionales
    • Haz que los pescadores tengan distintos niveles de ética ambiental, de manera que algunos limpien el océano más a menudo que otros.
    • Implementa un “ranking sostenible” al final del programa, donde se valore no solo quién pescó más peces, sino quién mantuvo el océano en mejor estado.
    • Permite que, si la contaminación llega a niveles extremos, los pescadores tengan que dejar de pescar hasta que se recupere el entorno.
    • Simular varios días de pesca, mostrando la evolución del sistema con printf y colores si lo deseas.

    • Utilizar variables, constantes, expresiones, conversiones y porcentajes.
    • Construir clases con atributos privados, constructores, métodos, parámetros y retornos.
    • Comprender referencias compartidas, modificación de objetos y sustitución de referencias.

    • Implementar listados simplemente enlazados a partir de interfaces documentadas.
    • Separar modelo y presentación para reutilizar las reglas en consola y JavaFX.
    • Utilizar excepciones, aserciones, Javadoc, pruebas y depuración.

    No utilices arrays, matrices, colecciones de Java ni ficheros para guardar partidas. Solo la interfaz IListado<T> declara un parámetro genérico: implementaremos tres listados y tres nodos concretos. La firma estándar main(String[] args) y los mecanismos internos de JavaFX proporcionados no forman parte de esa restricción.

    Reglas del juego

    1. El tablero tiene dimensiones positivas. Sus casillas son transitables salvo las ocupadas por piedras. Los bordes son límites, no casillas adicionales.
    2. El personaje se mueve una casilla con W, A, S o D, sin diagonales ni salidas del tablero.
    3. Si la casilla siguiente no contiene piedra, el personaje puede entrar.
    4. Si contiene una piedra, solo puede empujarla si la casilla inmediatamente posterior está dentro del tablero y no contiene otra piedra.
    5. No puede arrastrar piedras ni empujar dos a la vez. Si el intento está bloqueado, no cambia ninguna posición ni contador.
    6. Los destinos no son obstáculos: pueden estar bajo el personaje o una piedra y no desaparecen al retirarlos.
    7. Hay la misma cantidad positiva de piedras y destinos. El nivel se resuelve cuando todos los destinos están cubiertos por piedras.
    8. Una vez resuelto, se bloquean los movimientos. «Siguiente nivel» avanza si quedan niveles; resolver el último completa la partida.
    9. «Reiniciar» restaura las posiciones iniciales y pone los contadores del nivel a cero, incluso si ya estaba resuelto. No cambia de nivel.

    Cada desplazamiento válido suma un movimiento. Si además desplaza una piedra, suma un empuje. Entrar en un destino vacío no cuenta como empuje.

    Coordenadas y representación

    La esquina superior izquierda es (0, 0). x aumenta hacia la derecha e y hacia abajo. Son válidas 0 ≤ x < anchura y 0 ≤ y < altura.

    No necesitas almacenar cada casilla. Para consultar (x, y), compara esas coordenadas con el personaje y recorre los listados. Para dibujar el tablero, las vistas recorren filas y columnas con bucles anidados.

    SímboloSignificado
    .Casilla vacía.
    JPersonaje.
    PPiedra.
    DDestino vacío.
    *Piedra sobre destino.
    +Personaje sobre destino.

    getCasilla devuelve esos símbolos. JavaFX los dibuja gráficamente y la consola los representa con texto. El modelo no elige colores ni imprime.

    Listados simplemente enlazados

    El contrato común es IListado<T>: T representa el tipo de elemento. Implementa tres clases concretas: ListadoPiedras implements IListado<Piedra>, ListadoDestinos implements IListado<Destino> y ListadoNiveles implements IListado<Nivel>.

    IListado<Piedra> piedras = new ListadoPiedras();
IListado<Destino> destinos = new ListadoDestinos();
IListado<Nivel> niveles = new ListadoNiveles();

    Solo la interfaz declara T. Cada listado utiliza su nodo específico proporcionado: NodoPiedra, NodoDestino o NodoNivel. Cada nodo guarda un objeto de su tipo y apunta al siguiente nodo del mismo tipo.

    Cada listado mantiene su primer nodo y cantidad. Cada nodo guarda una referencia al objeto y otra al siguiente nodo; el último apunta a null. Un listado vacío no tiene primer nodo.

    primero → nodo → nodo → nodo → null
            ↓      ↓      ↓
          objeto objeto objeto
    MétodoContrato
    incluir(elemento)Añade al final la misma referencia. Rechaza null y una referencia ya incluida.
    obtener(indice)Devuelve la referencia de esa posición. Los índices empiezan en cero.
    eliminar(indice)Retira y devuelve el objeto, conservando el orden de los demás.
    sustituir(indice, elemento)Reemplaza una referencia y devuelve la anterior, sin cambiar la cantidad. Rechaza null o una referencia presente en otra posición.

    Un índice inexistente debe provocar IndexOutOfBoundsException, no un acceso accidental a null. Los errores no deben alterar el listado. Sustituir un elemento por su misma referencia es válido.

    Editar no es sustituir: cambiar las coordenadas de una piedra obtenida modifica el mismo objeto del listado. sustituir cambia qué objeto ocupa una posición. Dos objetos distintos con iguales datos no son una referencia duplicada; las colisiones de coordenadas las comprueba el nivel.

    Clases del modelo

    • Personaje: coordenadas actuales y coordenadas iniciales inmutables; consultas, cambio de posición, reinicio y descripción. Rechaza coordenadas negativas.
    • Piedra: posición y reinicio de un bloque. No conoce a la siguiente piedra: ese enlace está en el nodo.
    • Destino: coordenadas inmutables y descripción. Su ocupación se calcula consultando posiciones; no necesita guardar otro estado que pueda quedar desactualizado.
    • Nivel: título, dimensiones, personaje, listados y contadores. Valida la configuración, busca elementos, consulta casillas, realiza movimientos, reinicia y comprueba la victoria.
    • Juego: listado de niveles, índice actual y mensaje de resultado. Implementa Partida, traduce direcciones y coordina la progresión.

    Antes de un empuje, comprueba todo el movimiento. No muevas primero al personaje para descubrir después que la piedra estaba bloqueada.

    Reiniciar debe restaurar coordenadas guardadas como valores. Tener dos referencias a la misma piedra no crea una copia de su estado anterior.

    Tres niveles iniciales

    Constantes.NIVELES contiene un String con los tres escenarios. La primera línea de cada bloque es su título; después aparecen las filas del tablero. Una línea --- separa niveles. En los escenarios dados, el personaje comienza en (1, 2), pero la carga debe deducirlo del símbolo, no asumirlo.

    public class Constantes {

            "Primer empuje\n"

            + "......\n"
            + "......\n";
}

    Implementa Utilidades.cargarNiveles(), que carga la constante, y Utilidades.cargarNiveles(String texto), que interpreta cualquier texto con ese formato y devuelve IListado<Nivel>. Utiliza indexOf, substring, charAt y bucles, sin split, arrays ni colecciones.

    1. Separa cada bloque y extrae el título.
    2. Deduce la anchura por los caracteres de una fila y la altura por el número de filas. Todas deben medir lo mismo.
    3. Localiza el único personaje y crea el nivel. Crea piedras y destinos según los símbolos y añádelos a sus listados. * crea piedra y destino; +, personaje y destino.
    4. Valida el nivel e inclúyelo en el listado. Cada carga debe construir objetos nuevos.

    Admite saltos de línea LF y CRLF, con o sin salto final. Rechaza títulos o niveles vacíos, filas desiguales, símbolos desconocidos, personajes ausentes o repetidos y cantidades de piedras y destinos distintas o no positivas. No debe haber separador antes del primer nivel ni después del último.

    Estos son los datos que se obtienen al interpretar el texto proporcionado. Las posiciones se expresan como (x, y).

    NivelDimensionesPiedrasDestinos
    1. Primer empuje6 × 5(2, 2)(4, 2)
    2. Dos entregas7 × 6(2, 2), (4, 3)(5, 2), (5, 3)
    3. Tres caminos8 × 7(2, 2), (3, 3), (5, 4)(6, 2), (6, 3), (6, 4)

    Los niveles son resolubles e independientes. Reiniciar uno no altera los demás. El número mostrado empieza en uno; los índices del listado empiezan en cero.

    Editar y añadir niveles

    Abre src/main/java/edu/masanz/da/ut4/configuracion/Constantes.java y modifica el texto de NIVELES. No necesitas crear otra clase ni escribir coordenadas en el código.

    • Editar: cambia el título o sustituye los símbolos de las filas para mover el personaje, las piedras y los destinos. Utiliza puntos para las casillas vacías, no espacios.
    • Cambiar dimensiones: añade o elimina caracteres en todas las filas para cambiar la anchura; añade o elimina filas para cambiar la altura. El tablero debe seguir siendo rectangular.
    • Añadir: al final del último tablero, añade una línea ---, el título nuevo y sus filas. Conserva \n al final de cada línea del String y deja el punto y coma únicamente al final de toda la constante.
    • Reordenar: cambia el orden de los bloques completos. Ese será el orden de juego; no hay que asignarles un número manualmente.

    Por ejemplo, para añadir un cuarto nivel, retira el punto y coma de la última línea actual y continúa la concatenación con este bloque:

                + "---\n"
            + "Mi nuevo nivel\n"
            + "......\n"
            + ".JP.D.\n"
            + "......\n";

    Incluye un único personaje (J o +) y la misma cantidad positiva de piedras y destinos. Recuerda que * cuenta como piedra y destino, y + como personaje y destino. No dejes líneas vacías ni un separador después del último tablero.

    Guarda los cambios y vuelve a ejecutar MainConsola o MainJavaFX para reconstruir la partida. Con el cargador implementado, la cantidad de niveles y sus dimensiones se deducen del texto. Prueba siempre que el nuevo mapa se pueda resolver: tener un formato válido no garantiza que las piedras puedan llegar a sus destinos.

    Static, azar y conversiones

    • Utilidades.cargarNiveles() convierte los datos de Constantes en objetos. Utilidades es una clase normal con métodos estáticos, sin final ni constructor privado.
    • Utilidades.generarCodigo() utiliza Random y devuelve un entero entre 1000 y 9999. Identifica visualmente la partida; no tiene que ser único.
    • Utilidades.calcularPorcentaje(parte, total) devuelve un double entre 0 y 100. Valida que el total sea positivo y que la parte esté entre cero y el total. Evita la división entera.
    • Juego.getPartidasCreadas() consulta un contador estático de construcciones válidas. Reiniciar o avanzar no lo incrementa.
    • El código se genera una vez por partida: no cambia al dibujar o reiniciar.
    • Posiciones, movimientos y nivel actual son datos de instancia: dos partidas no comparten sus tableros.

    La consola proporcionada convierte opciones con Integer.parseInt y captura NumberFormatException. Lee y explica ese código: distingue un texto no numérico de un número que queda fuera del menú.

    Dos formas de ejecutar

    Trabajaremos desde IntelliJ IDEA. El paquete edu.masanz.da.ut4.app contiene dos clases con un método main para elegir cómo ejecutar el mismo juego:

    • MainConsola: inicia la versión de texto. La entrada y salida aparecen en la ventana de ejecución de IntelliJ.
    • MainJavaFX: abre una ventana gráfica con el tablero, los botones y los controles de teclado.

    Abre la clase elegida y pulsa el triángulo verde junto a su método main, o haz clic derecho sobre la clase y selecciona Run. Para depurar, utiliza Debug. Ejecuta MainJavaFX, no AplicacionJavaFX directamente.

    Antes de ejecutar, abre el proyecto como Maven mediante su pom.xml, selecciona JDK 17 y espera a que IntelliJ termine de cargar las dependencias. Ambas clases utilizan las dependencias Maven del proyecto; no necesitas copiar bibliotecas JavaFX manualmente.

    W, A, S y D son las direcciones; R reinicia y N solicita avanzar. JavaFX ofrece botones. En consola, Q sale y el menú numérico admite 0 salir, 1 reiniciar, 2 avanzar y 3 cargar una partida nueva.

    Ambas vistas llaman al contrato Partida. Una misma secuencia de acciones sobre partidas nuevas debe producir las mismas posiciones, contadores y victoria. No copies las reglas en las vistas.

    Excepciones, aserciones y pruebas

    Utiliza excepciones estándar de Java, sin crear clases de excepción propias: IllegalArgumentException para datos o argumentos no válidos e IndexOutOfBoundsException para índices inexistentes. Un bloqueo normal se comunica con false, no con una excepción.

    Los métodos pendientes de la base lanzan UnsupportedOperationException para mostrar un aviso o activar la vista previa. Retira ese aviso al implementar cada método; no lo utilices para errores de datos.

    Escribe una clase de comprobaciones propia para provocar y capturar un índice inexistente, comprobar referencias compartidas y probar construcciones rechazadas. No captures todos los errores para continuar como si no ocurriera nada.

    Añade al menos dos aserciones sobre invariantes internas: por ejemplo, la relación entre empujes y movimientos o la permanencia del personaje dentro del mapa. No sustituyen validaciones ni deben modificar datos. Actívalas con -ea al depurar.
