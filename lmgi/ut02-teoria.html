    2.1 ¿Qué es XSD?

    XSD permite definir qué estructura, elementos, atributos y tipos de datos debe cumplir un documento XML para considerarse válido.

    Además de esta documentación de clase, puedes consultar la documentación completa sobre XSD en W3Schools XML Schema Tutorial.

    Idea principal

    XSD significa XML Schema Definition. Un XSD es un documento que describe las reglas que debe cumplir otro documento XML.

    En la UT1 vimos que un XML puede estar bien formado: etiquetas cerradas, anidadas correctamente, un único elemento raíz, atributos entre comillas, etc. Pero eso no garantiza que el documento tenga los datos correctos.

    <alumno>
  <nombre>Ane</nombre>
  <edad>diecisiete</edad>
</alumno>

    Este XML puede estar bien formado, pero quizá para nuestra aplicación la edad debe ser un número entero. XSD sirve precisamente para definir ese tipo de reglas.

    Bien formado no es lo mismo que válido

    Concepto Qué comprueba Ejemplo
    XML bien formado Que la sintaxis XML es correcta. Las etiquetas se abren y cierran bien.
    XML válido Que el XML cumple las reglas de un esquema. <edad> debe contener un número entero.

    Enfoque de esta unidad

    En esta unidad trabajaremos con XSD. Los DTD pueden aparecer como referencia o venir dados, pero el trabajo principal será crear, leer y modificar documentos XML en función de esquemas XSD.

    La pregunta habitual será: ¿este XML cumple el XSD? Si no lo cumple, tendremos que detectar por qué y corregir el XML o el esquema según el caso.

    2.2 Estructura básica de un XSD

    Un XSD también es un documento XML, pero utiliza etiquetas propias del vocabulario XML Schema.

    La etiqueta raíz <xs:schema>

    Todo esquema XSD suele comenzar con la etiqueta <xs:schema>. El prefijo xs indica que estamos usando elementos del lenguaje XML Schema.

    <?xml version="1.0" encoding="UTF-8"?>
<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">

  <!-- Aquí se definen las reglas del XML -->

</xs:schema>

    La parte xmlns:xs="http://www.w3.org/2001/XMLSchema" declara el espacio de nombres de XSD. Gracias a ello, etiquetas como <xs:element> o <xs:complexType> tienen significado para un validador.

    Ejemplo mínimo

    Este XSD define que el XML debe tener un elemento llamado <mensaje> cuyo contenido será texto:

    <xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
  <xs:element name="mensaje" type="xs:string" />
</xs:schema>

    Con ese esquema, este XML sería válido:

    <mensaje>Hola XML</mensaje>

    Pero este otro no cumpliría la regla, porque la raíz no se llama <mensaje>:

    <texto>Hola XML</texto>

    Relación entre XML y XSD

    Un XML puede indicar qué esquema XSD debe usarse para validarlo. Para ello se suelen usar atributos relacionados con xsi y schemaLocation.

    <alumno
  xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  xsi:noNamespaceSchemaLocation="alumno.xsd">
  <nombre>Ane</nombre>
  <edad>17</edad>
</alumno>

    En clase será habitual trabajar con dos ficheros: un XML con datos y un XSD con las reglas que debe cumplir.

    2.3 Elementos simples, tipos de datos y atributos

    XSD permite indicar qué elementos existen, qué tipo de dato contienen y qué atributos pueden usar.

    Elementos simples

    Un elemento simple contiene texto, pero no contiene otros elementos ni atributos propios.

    <nombre>Ane</nombre>
<edad>17</edad>
<fechaNacimiento>2009-04-18</fechaNacimiento>

    En XSD se pueden definir así:

    <xs:element name="nombre" type="xs:string" />
<xs:element name="edad" type="xs:integer" />
<xs:element name="fechaNacimiento" type="xs:date" />

    Tipos de datos habituales

    Tipo XSD Qué representa Ejemplo válido
    xs:string Texto Ane
    xs:integer Número entero 17
    xs:decimal Número con decimales 8.75
    xs:boolean Verdadero o falso true, false, 1, 0
    xs:date Fecha 2026-09-24

    Atributos

    Los atributos también pueden declararse en XSD. Normalmente se definen dentro de un tipo complejo, porque pertenecen a un elemento.

    <alumno id="A001">
  <nombre>Ane</nombre>
</alumno>
    <xs:attribute name="id" type="xs:string" use="required" />

    El atributo use="required" indica que ese atributo es obligatorio. Si no aparece en el XML, el documento no será válido respecto al XSD.

    2.4 Tipos complejos y secuencias

    Los tipos complejos permiten definir elementos que contienen otros elementos, atributos o ambas cosas.

    Elementos con otros elementos dentro

    Muchos documentos XML tienen elementos que agrupan información. Por ejemplo, un elemento <alumno> puede contener <nombre>, <edad> y <curso>.

    <alumno>
  <nombre>Ane</nombre>
  <edad>17</edad>
  <curso>1 DAM</curso>
</alumno>

    En XSD, ese elemento se define con <xs:complexType>:

    <xs:element name="alumno">
  <xs:complexType>
    <xs:sequence>
      <xs:element name="nombre" type="xs:string" />
      <xs:element name="edad" type="xs:integer" />
      <xs:element name="curso" type="xs:string" />
    </xs:sequence>
  </xs:complexType>
</xs:element>

    La importancia del orden

    <xs:sequence> indica que los elementos hijos deben aparecer en el mismo orden en el que se han declarado.

    XML Resultado Motivo
    <nombre>, <edad>, <curso> Válido Respeta el orden del XSD.
    <edad>, <nombre>, <curso> No válido No respeta la secuencia definida.

    Repeticiones y obligatoriedad

    Con minOccurs y maxOccurs podemos indicar cuántas veces puede aparecer un elemento.

    Si no escribimos estos atributos, XSD entiende que el elemento debe aparecer exactamente una vez.

    <xs:element name="telefono" type="xs:string" minOccurs="0" maxOccurs="unbounded" />

    Este ejemplo indica que <telefono> puede no aparecer, aparecer una vez o aparecer muchas veces.

    Atributo Qué controla Valores habituales Valor por defecto
    minOccurs Número mínimo de veces que debe aparecer el elemento. 0, 1, 2, 3... 1
    maxOccurs Número máximo de veces que puede aparecer el elemento. 1, 2, 3..., unbounded 1

    La palabra unbounded significa que no hay un límite máximo concreto: el elemento puede repetirse tantas veces como sea necesario.

    Definición Cómo se interpreta Ejemplo de uso
    minOccurs="1" maxOccurs="1" Debe aparecer exactamente una vez. Un nombre obligatorio.
    minOccurs="0" maxOccurs="1" Puede no aparecer, pero si aparece solo puede hacerlo una vez. Un segundo apellido opcional.
    minOccurs="0" maxOccurs="unbounded" Puede no aparecer o puede aparecer muchas veces. Una lista opcional de teléfonos.
    minOccurs="1" maxOccurs="unbounded" Debe aparecer al menos una vez y puede repetirse. Una lista de módulos matriculados.
    minOccurs="2" maxOccurs="4" Debe aparecer como mínimo dos veces y como máximo cuatro. Entre dos y cuatro ejercicios entregados. 
    <xs:element name="nombre" type="xs:string" />
<!-- Equivale a minOccurs="1" maxOccurs="1" -->

<xs:element name="segundoApellido" type="xs:string" minOccurs="0" maxOccurs="1" />
<!-- Opcional: puede no salir -->

<xs:element name="telefono" type="xs:string" minOccurs="0" maxOccurs="unbounded" />
<!-- Opcional y repetible -->

    2.5 Restricciones y validación

    Las restricciones permiten limitar los valores aceptados por un elemento o atributo.

    Restricciones numéricas

    Podemos indicar valores mínimos y máximos. Por ejemplo, una edad entre 0 y 120:

    <xs:element name="edad">
  <xs:simpleType>
    <xs:restriction base="xs:integer">
      <xs:minInclusive value="0" />
      <xs:maxInclusive value="120" />
    </xs:restriction>
  </xs:simpleType>
</xs:element>

    <edad>17</edad> sería válido, pero <edad>200</edad> no lo sería.

    Valores permitidos

    Con <xs:enumeration> podemos limitar un valor a una lista cerrada de opciones.

    <xs:element name="modalidad">
  <xs:simpleType>
    <xs:restriction base="xs:string">
      <xs:enumeration value="DAM" />
      <xs:enumeration value="DAW" />
      <xs:enumeration value="ASIR" />
    </xs:restriction>
  </xs:simpleType>
</xs:element>

    En este caso, <modalidad>DAM</modalidad> sería válido, pero <modalidad>Bachillerato</modalidad> no.

    Patrones

    Con <xs:pattern> podemos obligar a que un texto siga una forma concreta. Por ejemplo, un código de alumno formado por la letra A y tres dígitos:

    <xs:element name="codigo">
  <xs:simpleType>
    <xs:restriction base="xs:string">
      <xs:pattern value="A[0-9][0-9][0-9]" />
    </xs:restriction>
  </xs:simpleType>
</xs:element>

    <codigo>A125</codigo> sería válido, pero <codigo>AL125</codigo> no.

    Cómo pensaremos la validación

    Para validar un XML frente a un XSD seguiremos siempre una idea sencilla:

    • Leer el XSD para localizar la raíz esperada.
    • Comprobar qué elementos y atributos son obligatorios.
    • Revisar el orden definido por las secuencias.
    • Comprobar los tipos de datos.
    • Aplicar restricciones: rangos, enumeraciones, patrones y repeticiones.

    Durante la unidad trabajaremos mucho modificando XML para que cumplan un XSD dado, y también modificando XSD para expresar nuevas reglas.

    2.6 Ejemplos completos: mezclando reglas XSD

    En un XSD real es habitual mezclar elementos simples, restricciones, atributos, tipos complejos y elementos anidados.

    Por qué necesitamos ejemplos completos

    Hasta ahora hemos visto las piezas por separado: elementos, atributos, secuencias, tipos de datos y restricciones. En la práctica, un esquema XSD suele combinar varias de estas piezas al mismo tiempo.

    La idea es leer el XSD como si fuera un contrato: indica qué etiquetas puede tener el XML, en qué orden, con qué atributos y qué valores se consideran válidos.

    Ejemplo 1: alumno con restricciones y atributos

    Este XML representa un alumno. Tiene un atributo obligatorio id, elementos simples y varios valores restringidos.

    <alumno id="A125">
  <nombre>Nerea</nombre>
  <edad>17</edad>
  <modalidad>DAM</modalidad>
  <notaMedia>8.4</notaMedia>
</alumno>

    Un posible XSD para validarlo sería:

    <xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
  <xs:element name="alumno">
    <xs:complexType>
      <xs:sequence>
        <xs:element name="nombre" type="xs:string" />

        <xs:element name="edad">
          <xs:simpleType>
            <xs:restriction base="xs:integer">
              <xs:minInclusive value="16" />
              <xs:maxInclusive value="65" />
            </xs:restriction>
          </xs:simpleType>
        </xs:element>

        <xs:element name="modalidad">
          <xs:simpleType>
            <xs:restriction base="xs:string">
              <xs:enumeration value="DAM" />
              <xs:enumeration value="DAW" />
            </xs:restriction>
          </xs:simpleType>
        </xs:element>

        <xs:element name="notaMedia">
          <xs:simpleType>
            <xs:restriction base="xs:decimal">
              <xs:minInclusive value="0" />
              <xs:maxInclusive value="10" />
            </xs:restriction>
          </xs:simpleType>
        </xs:element>
      </xs:sequence>

      <xs:attribute name="id" use="required">
        <xs:simpleType>
          <xs:restriction base="xs:string">
            <xs:pattern value="A[0-9][0-9][0-9]" />
          </xs:restriction>
        </xs:simpleType>
      </xs:attribute>
    </xs:complexType>
  </xs:element>
</xs:schema>

    En este ejemplo se mezclan varias reglas: el atributo id es obligatorio, la edad tiene rango, la modalidad tiene valores permitidos y la nota media debe estar entre 0 y 10.

    Ejemplo 2: tipo complejo dentro de otro tipo complejo

    Un tipo complejo puede contener otro elemento que, a su vez, también tenga estructura interna. Por ejemplo, una matrícula contiene los datos de un alumno y los datos de un módulo.

    <matricula curso="2026-2027">
  <alumno>
    <nombre>Iker</nombre>
    <email>iker@example.com</email>
  </alumno>
  <modulo codigo="LMSGI">
    <nombre>Lenguaje de Marcas</nombre>
    <horas>128</horas>
  </modulo>
</matricula>

    El XSD puede definir una estructura anidada:

    <xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
  <xs:element name="matricula">
    <xs:complexType>
      <xs:sequence>
        <xs:element name="alumno">
          <xs:complexType>
            <xs:sequence>
              <xs:element name="nombre" type="xs:string" />
              <xs:element name="email">
                <xs:simpleType>
                  <xs:restriction base="xs:string">
                    <xs:pattern value=".+@.+" />
                  </xs:restriction>
                </xs:simpleType>
              </xs:element>
            </xs:sequence>
          </xs:complexType>
        </xs:element>

        <xs:element name="modulo">
          <xs:complexType>
            <xs:sequence>
              <xs:element name="nombre" type="xs:string" />
              <xs:element name="horas">
                <xs:simpleType>
                  <xs:restriction base="xs:integer">
                    <xs:minInclusive value="1" />
                  </xs:restriction>
                </xs:simpleType>
              </xs:element>
            </xs:sequence>
            <xs:attribute name="codigo" type="xs:string" use="required" />
          </xs:complexType>
        </xs:element>
      </xs:sequence>

      <xs:attribute name="curso" type="xs:string" use="required" />
    </xs:complexType>
  </xs:element>
</xs:schema>

    Aquí aparecen dos niveles de estructura: <matricula> contiene <alumno> y <modulo>, y ambos tienen sus propios elementos internos.

    Ejemplo 3: contenido simple con atributo

    A veces un elemento no tiene hijos, solo texto, pero además necesita atributos. Por ejemplo, una nota puede tener como contenido el valor numérico y como atributo la convocatoria.

    <nota convocatoria="ordinaria">8.5</nota>

    Este caso tiene un poco más de miga: no basta con declarar un <xs:simpleType>, porque los tipos simples no pueden tener atributos. Para tener texto y atributos a la vez necesitamos un <xs:complexType> con <xs:simpleContent>.

    <xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
  <xs:element name="nota">
    <xs:complexType>
      <xs:simpleContent>
        <xs:extension base="tipoNota">
          <xs:attribute name="convocatoria" use="required">
            <xs:simpleType>
              <xs:restriction base="xs:string">
                <xs:enumeration value="ordinaria" />
                <xs:enumeration value="extraordinaria" />
              </xs:restriction>
            </xs:simpleType>
          </xs:attribute>
        </xs:extension>
      </xs:simpleContent>
    </xs:complexType>
  </xs:element>

  <xs:simpleType name="tipoNota">
    <xs:restriction base="xs:decimal">
      <xs:minInclusive value="0" />
      <xs:maxInclusive value="10" />
    </xs:restriction>
  </xs:simpleType>
</xs:schema>

    En este ejemplo, el contenido de <nota> debe cumplir el tipo tipoNota, pero además el elemento debe tener un atributo convocatoria con uno de los valores permitidos.

    XML Resultado Motivo
    <nota convocatoria="ordinaria">8.5</nota> Válido La nota está entre 0 y 10, y la convocatoria está permitida.
    <nota convocatoria="final">8.5</nota> No válido final no aparece en la enumeración.
    <nota convocatoria="ordinaria">12</nota> No válido El contenido no respeta el rango definido en tipoNota.

    Cómo leer estos ejemplos

    • Primero localiza el elemento raíz del XML.
    • Después busca en el XSD el <xs:element> con ese nombre.
    • Si tiene <xs:complexType>, revisa qué elementos hijos permite.
    • Si aparece <xs:sequence>, respeta el orden indicado.
    • Comprueba atributos obligatorios con use="required".
    • Por último, revisa restricciones como rangos, enumeraciones o patrones.

    2.7 Definir tipos propios y reutilizarlos

    XSD permite crear tipos propios para reutilizar reglas en distintas partes del esquema.

    Por qué crear tipos propios

    Si una misma regla aparece varias veces, no tiene sentido escribirla una y otra vez. En XSD podemos definir un tipo una sola vez y reutilizarlo después.

    Esto hace que el esquema sea más claro, más fácil de mantener y menos propenso a errores.

    Tipos simples propios

    Un tipo simple propio sirve para dar nombre a una restricción. Por ejemplo, podemos definir un tipo para notas entre 0 y 10.

    <xs:simpleType name="tipoNota">
  <xs:restriction base="xs:decimal">
    <xs:minInclusive value="0" />
    <xs:maxInclusive value="10" />
  </xs:restriction>
</xs:simpleType>

    Después, podemos reutilizarlo en varios elementos:

    <xs:element name="notaProgramacion" type="tipoNota" />
<xs:element name="notaMarcas" type="tipoNota" />
<xs:element name="notaBasesDatos" type="tipoNota" />

    Si más adelante cambiamos el rango de notas, solo tendremos que modificar tipoNota.

    Otro tipo simple: código de alumno

    También podemos crear un tipo propio para un patrón concreto:

    <xs:simpleType name="tipoCodigoAlumno">
  <xs:restriction base="xs:string">
    <xs:pattern value="A[0-9][0-9][0-9]" />
  </xs:restriction>
</xs:simpleType>

    Y usarlo, por ejemplo, en un atributo:

    <xs:attribute name="id" type="tipoCodigoAlumno" use="required" />

    Tipos complejos propios

    Los tipos complejos propios sirven para reutilizar estructuras completas. Por ejemplo, podemos definir una dirección una vez:

    <xs:complexType name="tipoDireccion">
  <xs:sequence>
    <xs:element name="calle" type="xs:string" />
    <xs:element name="numero" type="xs:string" />
    <xs:element name="codigoPostal">
      <xs:simpleType>
        <xs:restriction base="xs:string">
          <xs:pattern value="[0-9][0-9][0-9][0-9][0-9]" />
        </xs:restriction>
      </xs:simpleType>
    </xs:element>
    <xs:element name="localidad" type="xs:string" />
  </xs:sequence>
</xs:complexType>

    Y después usarla en distintos elementos:

    <xs:element name="direccionAlumno" type="tipoDireccion" />
<xs:element name="direccionCentro" type="tipoDireccion" />

    Ejemplo completo con tipos reutilizables

    Este XML utiliza una estructura de alumno con dirección y notas:

    <alumno id="A125">
  <nombre>Nerea</nombre>
  <direccion>
    <calle>Calle Mayor</calle>
    <numero>12</numero>
    <codigoPostal>31001</codigoPostal>
    <localidad>Pamplona</localidad>
  </direccion>
  <notaProgramacion>8.5</notaProgramacion>
  <notaMarcas>9</notaMarcas>
</alumno>

    Un esquema XSD con tipos propios podría ser:

    <xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
  <xs:simpleType name="tipoCodigoAlumno">
    <xs:restriction base="xs:string">
      <xs:pattern value="A[0-9][0-9][0-9]" />
    </xs:restriction>
  </xs:simpleType>

  <xs:simpleType name="tipoNota">
    <xs:restriction base="xs:decimal">
      <xs:minInclusive value="0" />
      <xs:maxInclusive value="10" />
    </xs:restriction>
  </xs:simpleType>

  <xs:complexType name="tipoDireccion">
    <xs:sequence>
      <xs:element name="calle" type="xs:string" />
      <xs:element name="numero" type="xs:string" />
      <xs:element name="codigoPostal" type="xs:string" />
      <xs:element name="localidad" type="xs:string" />
    </xs:sequence>
  </xs:complexType>

  <xs:element name="alumno">
    <xs:complexType>
      <xs:sequence>
        <xs:element name="nombre" type="xs:string" />
        <xs:element name="direccion" type="tipoDireccion" />
        <xs:element name="notaProgramacion" type="tipoNota" />
        <xs:element name="notaMarcas" type="tipoNota" />
      </xs:sequence>
      <xs:attribute name="id" type="tipoCodigoAlumno" use="required" />
    </xs:complexType>
  </xs:element>
</xs:schema>

    Reglas prácticas

    • Usa <xs:simpleType> propio cuando quieras reutilizar una restricción sobre texto, números, fechas, patrones o enumeraciones.
    • Usa <xs:complexType> propio cuando quieras reutilizar una estructura con elementos hijos o atributos.
    • Los tipos propios se declaran normalmente dentro de <xs:schema>, antes de utilizarlos.
    • Para usar un tipo propio, escribe su nombre en el atributo type.
